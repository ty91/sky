# 대화를 Sky 대화 ID로 식별하고 Slack 스레드와 백엔드 세션을 대화에 연결한다

앱이 Slack 없이 대화를 만들고 다시 열려면 대화의 정체성이 Slack 스레드 주소에 묶여 있지 않아야 한다. 대화는 Sky가 발급한 ID로 식별하며 Slack 스레드(`<channel>:<thread_ts>`)는 외부 연결로, Pi·Claude 세션은 대화에 딸린 백엔드 세션으로 관리한다. 하나의 Slack 스레드는 하나의 대화에만 연결되고, 대화도 provider별로 하나의 연결만 가진다. 대화 ID 형식은 UUID이며 내용에 의미를 두지 않는다.

## 백엔드 세션

대화는 백엔드별 세션 슬롯을 하나씩 가진다. 백엔드를 바꿨다가 되돌리면 이전 백엔드의 세션을 재개하고, 같은 백엔드에서 모델이나 에이전트가 달라지면 같은 대화 안에서 새 세션으로 교체한다. 교체된 세션의 이력은 보존하지 않는다. 백엔드 세션의 resume 정보는 모델이 대화를 이어가기 위한 것이며 앱 화면의 메시지 이력이 아니다. 화면 이력은 별도 영속화가 필요하고, 세션 복원만으로 복구된다고 가정하지 않는다.

## 모델 설정과 Slack 도구

`!model` 설정은 대화의 속성이다. 명령은 대화를 먼저 만들고 모델만 기록하므로 백엔드 세션이 없을 수 있다. 채널 스레드에서 멘션 없는 후속 메시지에 응답할지는 대화 존재가 아니라 현재 에이전트가 이어받을 수 있는 백엔드 세션의 존재로 판단한다. 대화 존재로 판단하면 `!model`만 입력한 스레드가 멘션 없이 응답을 받기 시작한다.

Slack 파일 첨부와 예약 도구는 대화의 Slack 연결에서 채널과 스레드를 얻는다. Slack 연결이 없는 대화에는 이 도구를 제공하지 않는다. 예약 실행은 전송할 채널을 작업 정의에서 명시적으로 받는다.

## 예약 실행

예약 작업의 실행 기록을 별도 테이블에 두고 실행마다 대화 ID를 하나 발급한다. 일회성 예약의 실행 한 번이나 반복 예약의 회차 하나가 실행 한 건이며, 에이전트 실패로 인한 재시도는 같은 실행의 attempt로 기록하고 같은 대화를 이어 쓴다. 전송에 성공하면 그 대화에 게시된 Slack 스레드를 연결하므로 사용자의 답장이 같은 백엔드 세션으로 이어진다. 전송하지 못한 실행의 대화는 연결 없이 남고, 실행 기록이 그 대화의 출처를 설명한다.

기존 구조는 `scheduled:<jobId>` 키로 턴을 실행한 뒤 전송된 스레드 키로 세션 포인터를 옮겼다. 이 방식은 대화가 키 문자열이라는 전제에 의존하고 전송하지 못한 실행을 설명하지 못한다. 실행 기록은 상태·attempt·시각·오류와 대화 ID만 보관하며 결과 본문 보관과 전송만 재시도하는 구조는 [ADR-0010](0010-separate-agent-runtime-from-slack.md)의 후속 과제로 남는다. 실행의 대화는 턴을 시작할 때 만들어지므로 실행 기록의 대화 ID에는 외래 키를 두지 않는다.

## 기존 데이터 전환

데몬은 시작 시 저장소를 전환한 뒤 다른 작업을 시작한다. 대화 스키마 v4의 각 키를 대화 하나로 옮기고, Slack 스레드 형식의 키에는 Slack 연결을 붙여 같은 백엔드 세션과 resume 정보·frozen system prompt를 유지한다. `thread_models`는 대화의 모델로 합친다. Slack 형식이 아닌 키(`scheduled:<jobId>` 등)는 연결 없는 대화가 되며 실행 기록을 거꾸로 만들지 않는다. 전환은 하나의 SQLite 트랜잭션이며 실패하면 v4 상태가 그대로 남는다.

transcript는 memory 입력이며 `transcripts/<대화 ID>/<session ID>.md`에 기록한다. 기존 Slack 스레드 키 디렉터리는 DB 전환으로 확정된 매핑을 따라 이동한다. memory 커서에 새 경로를 먼저 추가하고 디렉터리를 옮긴 뒤 이전 경로를 정리하므로, 중간에 중단되어도 다음 시작에서 이어지고 과거 transcript를 다시 처리하지 않는다. 매핑되지 않는 디렉터리는 그대로 둔다.

새 스키마는 이전 버전 바이너리가 읽지 못하며 기존처럼 기동을 거부한다. 다운그레이드는 지원하지 않는다.
