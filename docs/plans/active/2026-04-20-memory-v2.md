# Memory System v2 — 4계층 시간 차등 아키텍처

## Context

현재 claudeclaw의 메모리 시스템은 **단일 Memory Agent가 30분마다 모든 걸 한꺼번에 처리**한다:

- `src/agents/memory/agent.ts` — claude-opus-4-7, 30분 주기 cron
- L1 원문 저장 (`~/.claudeclaw/transcripts/<chatId>/<sessionId>.md`)은 실시간 append로 이미 동작 중
- 그러나 원문 → 단기 요약(`_recent.md`) → 장기 지식(people/projects/knowledge)까지를 **한 에이전트가 30분에 한 번씩 통합 처리**

### 문제점

1. **실시간성 공백** — 세션이 끝난 직후부터 다음 cron 틱까지 최대 30분간, 다른 세션에서는 방금 한 대화를 모름.
2. **역할 혼재** — "working memory 갱신"(실시간성 중요)과 "지식 그래프 큐레이션"(신중함 중요)이 같은 에이전트 안에서 경쟁.
3. **비용 비효율** — 모든 작업을 Opus가 처리. 단기 요약에는 과한 모델.
4. **주기 미분화** — 일간 consolidation / 주간 retrospection 같은 **긴 호흡의 정리**가 없음. `_recent.md`가 7일 범위를 다루지만 Memory Agent가 계속 append하면서 점점 길어지는 경향.

### 목표

메모리 시스템을 **업데이트 주기·모델·역할이 분리된 4계층**으로 재편한다. 시간축과 지식축을 모두 유지하되, 각 층의 리듬을 다르게 가져간다.

### Scope

**포함 (이 계획 전체):**
- 4계층 메모리 아키텍처 (L1/L2/L3/L4) 정의 및 구현
- 기존 Memory Agent 교체 (새 에이전트 이름도 `memory`로 유지)
- 볼트 구조 변경 (`daily/` 재정의, `weekly/` 신설, `_recent.md` 스펙 변경)
- L1 트랜스크립트 7일 아카이빙
- Slack 알림 말머리 규약

**제외:**
- Monthly/Yearly consolidation의 **에이전트 구현** (폴더/README만 선제 생성)
- 벡터 검색/임베딩 기반 조회 (시간 윈도우로 충분)
- L1 전체 검색 도구 (필요해지면 별도 계획)

**Phase별 범위:**
- **Phase 1**: L2 working memory 에이전트 신설 + 기존 Memory Agent 교체 (이번 계획의 주 타겟)
- **Phase 2**: L4 주간 consolidation
- **Phase 3**: L3 "꿈" 에이전트 (일간 지식 그래프 업데이트)
- **Phase 4**: L1 7일 아카이브 자동화

## Architecture

### 4계층 개요

```
[Slack DM / channel mentions]
         ↓ (실시간)
┌──────────────────────────────────────────────────────┐
│ L1: Raw Transcripts                                  │
│ ~/.claudeclaw/transcripts/<chatId>/<sessionId>.md    │
│ 실시간 append (이미 구현됨)                          │
│ 보관 기간: 7일 → 이후 archive/로 이동                │
└──────────────────────────────────────────────────────┘
         ↓ (5분 폴링, Sonnet)
┌──────────────────────────────────────────────────────┐
│ L2: Working Memory — `memory` agent                  │
│ 최근 24시간 윈도우 엄격                              │
│ memory/_recent.md 를 교체 방식으로 갱신              │
└──────────────────────────────────────────────────────┘
         ↓ (매일 02:00 KST, Opus)
┌──────────────────────────────────────────────────────┐
│ L3: Dream — `dream` agent [Phase 3]                  │
│ 전날 전체 트랜스크립트 소화                          │
│ people/projects/context/knowledge/ 업데이트          │
│ episodes/daily/YYYY-MM-DD.md 꿈 로그 기록            │
│ 길어진 문서(>600줄) split 허용, delete 금지          │
└──────────────────────────────────────────────────────┘
         ↓ (매주 월 03:00 KST, Opus)
┌──────────────────────────────────────────────────────┐
│ L4: Weekly — `weekly` agent [Phase 2]                │
│ 지난 주 트랜스크립트 + daily 꿈 로그 종합            │
│ episodes/weekly/YYYY-Www.md 생성                     │
└──────────────────────────────────────────────────────┘
   (Monthly / Yearly: 폴더 + 플레이스홀더 README만)
```

### 시간축 vs 지식축 책임 분담

| 축 | 책임 | 담당 레이어 |
|---|---|---|
| 🕐 시간축 | "언제 무슨 일이 있었나" | L1 원문, L2 `_recent`, L3 daily 꿈 로그, L4 weekly |
| 🧠 지식축 | "누가·무엇이·어떻게" (재사용 가능한 사실) | L3가 people/projects/context/knowledge 업데이트 |

L1/L2는 시간축 전담, L4는 시간축 요약, **L3만이 두 축을 잇는 다리** — 하루 치 시간축을 소화하여 지식축을 갱신하고, 그 행위의 로그를 daily 꿈 로그(시간축)에 남긴다.

## Design Decisions

| 질문 | 결정 | 근거 |
|------|------|------|
| L2 주기 | 5분 cron | "세션 종료" 개념 없음. 다른 세션에서 감지되기까지 최대 5분 지연 수용 가능. |
| L2 모델 | `claude-sonnet-4-6` (현 시점 최신 Sonnet, 2026-02 출시) | Opus 대비 비용 ~5배 저렴, 요약 품질 충분. L3/L4만 Opus. |
| L2 시간 윈도우 | 최근 24시간 엄격 | 범위 제한 없으면 LLM이 문서를 계속 늘림. 24h + 교체 방식으로 `_recent.md` 길이 상한. |
| L2 갱신 방식 | 전체 교체 (append 아님) | 매 실행마다 빈 문서에서 새로 생성. 누적 방지. |
| L3 delete 권한 | 금지 | 잘못된 삭제는 복구 어려움. add/update만 허용. |
| L3 split 규칙 | 600줄 초과 시 | 단순 임계값. 태영님이 쉽게 감 잡을 수 있는 숫자. |
| L3 분류 판단 | 자율 (index.md 가이드 참조) | 프롬프트에 분류 가이드 명시, 에이전트가 판단. |
| L4 저장 위치 | `memory/episodes/weekly/YYYY-Www.md` | ISO week number. 월요일 03:00이면 지난 일요일까지 포함. |
| Monthly/Yearly | 폴더 + README만 선제 생성 | 아키텍처 확장성 유지, 구현은 데이터 쌓이면 진행. |
| L1 회수 정책 | 7일 → `archive/` 이동 | 삭제 아닌 아카이브. 복구 가능, 디스크 부담은 적음. |
| 스케줄러 | 외부 cron 유지 | 봇 프로세스 장애가 메모리 파이프라인에 영향 없음. |
| 새 에이전트 이름 | `memory` (L2가 상속) | 기존 cron/CLI 재활용. L3는 `dream`, L4는 `weekly`. |
| Slack 알림 | L3/L4/Archive만 기존 `C0APGL1DKDH` 공유, 말머리 구분 | `[dream]`, `[weekly]`, `[archive]` |
| **L2 알림 정책** | **완전 차단 (항상 silent)** | 5분마다 돌아서 소음 과다. 실패 시 로그만 남기고, 성공/실패 모두 Slack 포스트 없음. |

## Volt 스펙 변경

### `_recent.md` — L2 전담으로 재정의

- **이전**: 7일 롤링, Memory Agent가 매 30분마다 append/갱신
- **이후**: 최근 24시간 working memory, L2(`memory` agent)가 5분마다 **전체 교체**
- frontmatter `window`는 항상 `최근 24시간 (기준: YYYY-MM-DD HH:MM KST)` 형식
- 섹션 구성은 유지 (🔥 진행 중 / 🎯 하이라이트 / ❓ 열린 질문) 하되 엄격하게 24h 범위

### `episodes/daily/YYYY-MM-DD.md` — L3 꿈 로그로 재정의

- **이전**: Memory Agent가 그날 대화 요약 기록
- **이후**: L3 dream 에이전트가 새벽 2시 꿈꾸면서 만든 **그날 밤의 정리 로그**
  - 어떤 문서를 어떻게 업데이트했는지 (add/update/split 내역)
  - 그날의 핵심 이벤트 + 지식 변화 요약
  - 다음 날 대화에서 참조 가능
- 파일명은 YYYY-MM-DD 그대로 유지 (Asia/Seoul)

### `episodes/weekly/YYYY-Www.md` — 신설

- L4 weekly 에이전트가 월요일 03:00에 생성
- ISO week number (예: `2026-W17.md`)
- 지난 주 daily 꿈 로그 7개 + 해당 주 트랜스크립트 기반 consolidation

### `episodes/monthly/`, `episodes/yearly/` — 폴더 + README 플레이스홀더

- `README.md`에 "미래의 Monthly/Yearly consolidation용 디렉토리" 명시
- 에이전트 구현은 데이터 쌓인 뒤 별도 계획으로

### `index.md` — 업데이트 필요

- Episodes 섹션에 `weekly/`, `monthly/`, `yearly/` 추가
- `_recent.md` 윈도우 스펙 갱신 (7일 → 24시간)
- `daily/` 용도 변경 반영 (요약 → 꿈 로그)

## Implementation Steps

### Phase 1: L2 Working Memory 에이전트 (이번 계획의 주 타겟)

> 기존 프롬프트/에이전트는 git history에 남으므로 별도 스냅샷 보존은 생략. Phase 3에서 L3 dream 에이전트 설계 시 `git log -- src/agents/memory/`로 참고.

#### Step 1.1: `src/agents/memory/prompt.ts` 전면 교체

기존 opus용 통합 프롬프트를 **L2 working memory 전담 프롬프트**로 재작성.

**핵심 원칙 (프롬프트에 반드시 포함):**

1. **역할 제한**: 너는 L2 working memory 담당. 장기 지식(people/projects/context/knowledge/)은 **절대 수정 금지**. L3 dream agent가 처리.
2. **대상 파일**: `memory/_recent.md` **한 파일만**. 다른 파일 수정 금지.
3. **시간 윈도우**: 최근 24시간. 24시간보다 오래된 이벤트는 **제거**.
4. **갱신 방식**: 매 실행마다 전체 교체 (append 아님). 문서 길이 폭증 방지.
5. **스킵 조건**: 지난 실행 이후 새 트랜스크립트가 없거나 의미 있는 변경이 없으면 `_recent.md` 그대로 두고 종료 (Slack 알림도 skip).
6. **분류 가이드**: `memory/index.md`를 매 실행마다 먼저 읽어 볼트 컨벤션 확인 (이건 읽기만).

**프롬프트 섹션 제안:**

```
# You are `memory` — the L2 Working Memory Agent

## Your Scope (STRICT)
- Target file: `memory/_recent.md` (ONLY this file)
- Time window: last 24 hours (strict — remove anything older)
- Update mode: FULL REPLACEMENT (no append)
- Read `memory/index.md` first to confirm vault conventions
- DO NOT modify people/, projects/, context/, knowledge/ — L3 dream agent handles those
- DO NOT modify episodes/daily/ — L3 dream agent handles those
- DO NOT modify episodes/weekly/ — L4 weekly agent handles those

## When to Skip
If the new transcript content since your last run contains no meaningful update
(e.g., small talk, already-captured facts), leave `_recent.md` unchanged and
output `SKIP` so the scheduler knows not to notify Slack.

## Output Format for `_recent.md`
... (기존 _recent.md 섹션 구조 유지: 🔥 진행 중 / 🎯 하이라이트 / ❓ 열린 질문)
```

### Phase 2: L4 Weekly Consolidation (개요)

- 신규 파일: `src/agents/weekly/` (`agent.ts`, `prompt.ts`)
- 모델: Opus
- 트리거: 월요일 03:00 KST (별도 cron entry)
- 입력: 지난 주 daily 꿈 로그 7개 + 해당 주 트랜스크립트 발췌
- 출력: `memory/episodes/weekly/YYYY-Www.md` 생성
- `monthly/`, `yearly/` 빈 폴더 + README 플레이스홀더 생성
- Slack 말머리: `[weekly]`

상세는 Phase 1 완료 후 별도 계획에서.

### Phase 3: L3 Dream Agent (개요)

- 신규 파일: `src/agents/dream/` (`agent.ts`, `prompt.ts`)
- 모델: Opus
- 트리거: 매일 02:00 KST
- 입력: 전날(KST) 전체 트랜스크립트
- 작업:
  1. `memory/index.md` 확인
  2. 전날 이벤트를 지식 그래프에 반영 (people/projects/context/knowledge create/update)
  3. 길어진 문서(>600줄) split (예: `이태영.md` → `이태영/profile.md` + `이태영/career.md`)
  4. `episodes/daily/YYYY-MM-DD.md`에 꿈 로그 기록 (무엇을 어떻게 바꿨는지)
  5. `index.md` 카탈로그 동기화
- 금지: delete, `_recent.md` 수정, weekly/monthly/yearly 수정
- Slack 말머리: `[dream]`

상세는 Phase 2 완료 후 별도 계획에서.

### Phase 4: L1 Archive Rotation (개요)

- 신규 스크립트 또는 명령: `claudeclaw transcripts archive`
- 트리거: 매일 04:00 KST (L3 완료 후)

## Open Questions

- **L2가 daily 꿈 로그를 참고해야 하나?** 24시간 윈도우를 벗어난 이벤트지만 "어제 저녁에 뭐 한 거 기억"이라는 대화에 도움될 수 있음. 일단 Phase 1에서는 **참고 안 함**으로 시작, 필요하면 추후 추가.
- **L2 SKIP 판단 기준의 엄격함** — "의미 있는 변경"을 LLM이 어떻게 판단할지 프롬프트로 가이드. 너무 엄격하면 최신 맥락 놓치고, 너무 느슨하면 알림 소음. Phase 1 운영 중 조정.
- **타임존 경계** — 5분 cron은 서버 타임존 따름. 24시간 윈도우는 프롬프트에서 KST 명시. 자정 경계에서 오버랩 최소화.
- **모델 업그레이드 시점** — Sonnet 4.5 → 다음 버전 나오면 바로 교체할지. 일단 현재 최신으로 고정.
